# 5. AI incident summaries are optional and never block incident resolution

## Status

Accepted (Phase 5).

## Context

On incident resolve, Pulsewatch asks an LLM to turn the incident's
check history into a plain-English summary ("down for 12 minutes,
timing out on every request, recovered without intervention" rather
than a table of timestamps and status codes). An LLM call is slower and
far less reliable than anything else in this app's write path. It can
time out, rate-limit (429), or simply be unavailable if no API key is
configured at all. The question is how much of the app that
unreliability is allowed to touch.

## Decision

The summary is generated by a separate Oban job
(`IncidentSummaryWorker`), enqueued *after* the incident is already
resolved, not inside the same transaction as the resolve itself, unlike
the alert job (see
[2. Oban for alerts and AI summaries](0002-oban-vs-tasks.md)). Resolving
an incident never waits on, and can never fail because of, the LLM. The
worker always returns `:ok` whether the LLM call succeeded or not. A
failure is logged, not silently dropped, but it never propagates back
to affect the incident record. The summary field is nullable and simply
absent from the UI and alert emails until (and unless) it's filled in.

A three-way `LlmClient` behaviour keeps this decoupled from any specific
provider: a real `AnthropicClient` (Req-backed, retries on 429/5xx), a
`DemoClient` returning canned, plausible-sounding outage descriptions,
and a Mox mock used in every test. `config/runtime.exs` picks
`DemoClient` automatically whenever `ANTHROPIC_API_KEY` isn't set, in
every environment except `:test`, which always uses the mock per
`CLAUDE.md`'s "never call a real LLM in tests" rule.

## Consequences

- Incident resolution, the operationally important part that alerts
  depend on, has zero dependency on an external LLM provider's uptime,
  latency, or rate limits. A summary is a nice-to-have layered on top,
  never a prerequisite.
- The demo-mode fallback means a fresh clone, a CI run, or a public demo
  deployment all show working "AI summaries" with zero setup and no real
  API key anywhere. That's a portfolio-relevant property, not just a
  convenience, since anyone evaluating this project shouldn't need to
  provision an Anthropic account first.
- The cost is a small window where an incident is resolved but its
  summary hasn't arrived yet. The summary job is scheduled to run a few
  seconds after the resolve alert, as a best-effort head start, but
  deliberately not a hard dependency: chaining them tightly risked a
  circular coupling between the Alerts and Ai contexts for a
  "sometimes" instead of an "always." The UI and resolve email both
  handle "no summary yet" as a normal, expected state rather than an
  error.
